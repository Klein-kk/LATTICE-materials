## 二、确认的根因（两条，均为操作符层面）

### 缺陷 A —— TJ 数组里的 kern 数值未用于还原空格（🔴 严重）

`TJ` 数组里的数字是**字间距调整量**（单位 1/1000 em，负值 = 间距变大），PDF 用它来"跳出"一个空格：

```
[(the)-194.6(cotton)-199.7(fabric)-197(industry)-196.9(\(Yu)-196(et)-193.9(al.)]TJ
   ↑          ↑           ↑          ↑            ↑         ↑
  这些 ~-195 的间隙 = 一个空格        而这些串内部是连着的
```

对照同一行里的**字距微调**：

```
(chem)-10.2(icals)     ← -10.2，属于字距调整，应连成 chemicals
```

两者相差近 20 倍，**区分度极高**：约 -195 是空格，约 -10 是字距。
本解析器 `walk()` 在遍历 `(...)` 字符串时**只解码字符串本身，完全忽略 TJ 数组里的数字** → 词间空格全部丢失。

**判定方案（阈值应基于字体自身的空格宽度，而非硬编码常数）**：
- 优先取该字体 `/Widths[32]`（简单字体）或 Type0 `/W` 中 space 的宽度（单位 /1000 em）；
- 取不到时退回经验值（本项目观察：Springer 与多数期刊用 0.20–0.35 em）；
- 规则：`|kern| / 1000 * fontSize >= 0.6 * spaceWidth` → 插入 1 个空格；
  `>= 1.6 * spaceWidth` → 插入 2 个空格（缩进/表格列间距）；否则不插。
- 对 CJK 安全：中文字符之间不会出现大 kern；且可先判字体是否为 CJK 编码再决定是否启用。

### 缺陷 B —— `TD` 操作符未被识别（🔴 严重）

内容流实际使用的是 **`TD`**（大写 D）：

```
13.9874 0 TD
-15.9904 -1.2462 TD
```

`TD` 与 `Td` 语义几乎相同（`TD` 额外设置 leading），但在 PDF 里是**两个不同的操作符**。
本解析器 `walk()` 只匹配 `ch === 'T' && content[i+1] === 'd'` → **`TD` 被完全忽略**。

后果：
- 换行事件丢失 → 段落与句子边界消失；
- 配合缺陷 A，整页文本被拼成一条无空格、无换行的长字符串；
- 直接导致 `extract.js` 的摘要推断（依赖"段落≥150 字符 + 句首大写"）**永远选不中**，摘要长度为 0；
- 章节切分（依赖行）退化为 1 段。

**修复方案**：`Td` / `TD` 一并识别（正则 `/^\s*([-\d.]+)\s+([-\d.]+)\s+(Td|TD)/`），
并用 y 位移判断是否换行、x 位移判断是否插入空格（`TD` 的 y 变化同样是换行信号）。

## 四、附带发现（供团队复核）

1. `0 Tc` / `0 Tw` —— 该 PDF 把字符间距与词间距都设为 0，因此**不存在**"用 Tw 生成空格"的路径，kern 是唯一信号。
2. 该 PDF **有 `/ToUnicode`（出现 4 次）**、**无 `/ObjStm`**、**无加密** —— 说明字体解码不是本次的问题，问题纯粹在"版面还原"这一层。
3. 内容流里字号为 `9.962599754`，空格 kern 约 `-195` → 换算间距 ≈ `195/1000 × 9.96 ≈ 1.94 pt`，与 9.96pt 字体的空格宽（约 0.25 em ≈ 2.5pt）同量级，**互相印证**上述阈值方案。
